## 第 2 页：速度曲线连接实验信号与后续物理判断

- **本页要回答的问题**：PDV 软件在实验链路中承担什么作用？
- **核心结论**：原始时间—电压记录本身不是最终物理结果；软件需要从时变拍频中提取速度历史，任何错误谱线都会向后传递到平台、起跳和加载过程判断。
- **正文内容**：
  1. 输入：两个采集量程的时间—电压序列。
  2. 中间量：时频能量与拍频脊线。
  3. 当前输出：基于显式波长的无符号表观速度。
  4. 后续：只有经过质量判断和物理修正后，才可支持更进一步的物理解释。
- **使用的图**：`实验信号 → 拍频脊线 → 表观速度 → 物理分析` 四阶段因果链。
- **图的来源**：当前代码调用链和项目规则重新绘制的示意图；不是实验结果图。
- **逻辑关系**：说明软件的重要性；下一页追问旧流程为什么难以提供可信证据链。

## 第 3 页：旧流程的核心风险不是界面陈旧，而是证据链不完整

- **本页要回答的问题**：现有旧软件参考为什么不能直接当作物理真值？
- **核心结论**：仓库中的旧软件速度文件只保留输出曲线与有限标记，来源和实验条件仍需确认；缺少完整参数、谱证据和质量状态，就无法从一条平滑曲线反推它是否跟踪了正确分支。
- **正文内容**：
  1. 旧输出被项目明确定位为“回归指纹”，不是物理真值。
  2. 当前可用标记仅区分 `measured / zero_masked`，不足以重建完整处理过程。
  3. 若波长、窗长、搜索带和人工选择不可追溯，结果无法可靠复现。
  4. 后果不是“图不好看”，而是错误分支可能被包装成连续曲线。
- **使用的图**：`缺少参数与质量证据 → 分支身份不清 → 连续曲线仍可能不可信` 风险链。
- **图的来源**：审计报告、`data/reference/legacy/README.md`、旧软件审计脚本。
- **逻辑关系**：从风险推导重建需求；下一页说明为什么选择 Python 工程化实现。

- **使用的图**：围绕 `core` 的四象限技术栈图。

## 第 5 页：新版处理链已打通表观速度闭环，物理修正仍被明确隔离

  - **正在完善**：弱信号判据、双通道质量决策、全时段开发预览的语义收口。
  - **尚未实现**：LiF/折射率/入射角修正、corrected velocity、有符号速度、自动通道融合、GUI。
- **使用的图**：红、橙、灰三态流程图。
- **图的来源**：`src/dps_studio/core/workflow/analysis.py`、`scripts/production_outputs.py`、审计报告第 17 节。

## 第 6 页：可信输入从只读原始数据、SI 单位和显式列映射开始

- **本页要回答的问题**：数据模型如何降低“读错数据、改坏数据”的风险？
- **核心结论**：同一 CSV 的两个电压列被读为两个独立 `SignalRecord`，内部统一秒、伏特和赫兹；源文件只读，非均匀采样被保留并标记，不静默插值、平滑或重采样。
- **正文内容**：
  1. `time=0, channel_1=1, channel_2=2` 写入单一 TOML 配置。
  2. 数组采用不可变存储，源数据哈希在真实运行中记录。
  3. 两通道保持独立，避免量程不同的数据在输入层被平均。
  4. 任何可靠性问题通过 NaN 和状态继续传递。
- **使用的图**：真实原始双通道事件窗口波形。
- **图的来源**：`assets/project_outputs/raw_voltage_event.png`，由任务内辅助脚本只读生成。
- **逻辑关系**：先保证输入可信；下一页说明 STFT 如何把时变频率显现出来。

## 第 7 页：STFT 将时变拍频转换为可追踪的时频脊线

- **本页要回答的问题**：为什么不能只做一次整体傅里叶变换？
- **核心结论**：PDV 拍频随时间变化，STFT 用滑动窗保留“何时出现哪一段频率”；窗长控制时间支持，hop 控制帧密度，NFFT 只加密频率网格而不等同于真实分辨率提升。
- **正文内容**：
  1. Balanced：Hann，`768 / 640 / 128 / 4096`。
  2. 当前 raw 下窗口约 19.2 ns，hop 约 3.2 ns。
  3. 数值搜索 `0.05–2.0 GHz`；完整单边谱到实际 Nyquist，约 20 GHz。
  4. 白色脊线是候选拍频轨迹，不是速度本身。
- **使用的图**：Balanced / 通道 1 的真实 `STFT + refined ridge`。
- **图的来源**：`assets/project_outputs/balanced_ch1_stft_ridge.png`。
- **逻辑关系**：把频率轨迹显现出来；下一页说明如何从频率换算表观速度。

## 第 8 页：脊线给出拍频轨迹，只有显式波长才能换算表观速度

- **本页要回答的问题**：频谱脊线如何变成速度曲线，边界在哪里？
- **核心结论**：候选脊线经三点对数幅值精修后，用 `v_app = λ₀ f_b / 2` 换算无符号表观速度；当前 `λ₀=1.55 µm` 仅是未确认的演示值，因此输出不能称为 LiF 修正后的真实界面速度。
- **正文内容**：
  1. 每帧闭搜索带内取最大谱峰，再做三点亚频点精修。
  2. 精修失败保持 NaN 和明确状态，不回退成“漂亮曲线”。
  3. PRE_EVENT 核心速度仍为 NaN；显示零只是画面假设。
  4. `apparent velocity` 与未来 `corrected velocity` 必须分开保存。
- **使用的图**：公式链 + Balanced / 通道 1 真实事件细节速度图。
- **图的来源**：`src/dps_studio/core/physics/velocity.py`、`assets/project_outputs/balanced_ch1_velocity_event.png`。
- **逻辑关系**：完成单通道数值闭环；下一页进入双通道和质量证据。

## 第 9 页：双通道必须独立分析；质量量只提供诊断证据

- **本页要回答的问题**：两个采集通道怎样比较，当前质量指标能做什么？
- **核心结论**：两个量程分别完成 STFT 和脊线分析；峰—背景、峰—竞争峰幅值对比度和连续性只描述当前谱结构，既不是正式 SNR，也不会自动选择或融合通道。
- **正文内容**：
  1. 两通道不做电压平均，也不做结果平均。
  2. 最近真实运行中通道 2 的描述性谱对比度较高，但不能据此自动判定更可信。
  3. 质量算法输出 dB 和状态，不删除、不平滑、不改写脊线。
  4. 正式 GOOD/BAD 阈值仍需实验标定。
- **使用的图**：四组真实描述性谱质量柱状图。
- **图的来源**：`assets/project_outputs/quality_diagnostics_summary.png` 及两份 `quality_summary.csv`。
- **逻辑关系**：说明质量量的能力边界；下一页解释软件架构怎样维持这些边界。

## 第 10 页：core/workflow 与 GUI 解耦，让数值链可以独立验证

- **本页要回答的问题**：软件架构如何保证结果可测试、可复现？
- **核心结论**：正式依赖方向是脚本入口 → TOML → `core.workflow` → IO/STFT/ridge/physics；core 不导入 GUI、绘图或 scripts，使每个数值对象和失败状态都能独立测试。
- **正文内容**：
  1. `core.io / models / time_frequency / ridge / physics / workflow` 承担正式数值职责。
  2. `scripts/production_outputs.py` 只负责编排落盘与绘图。
  3. `gui/` 仍是占位，未来只能调用 core 公共 API。
  4. manifest 记录配置、源哈希、Git 状态和生成文件。
- **使用的图**：分层架构与单向依赖图。
- **图的来源**：当前目录树、导入关系、审计报告第 17 节。

## 第 13 页：软件能运行不等于结果已达到科研使用标准

- **本页要回答的问题**：当前最关键的可信度缺口是什么？
- **核心结论**：基础闭环解决了“能否运行”，但正确分支、低频弱信号、物理波长和窗口修正仍缺少经实验条件确认的决策依据。
- **正文内容**：
  1. 脊线仍是逐帧最大峰，无最大跳频、动态规划或连续性约束。
  2. 质量量无正式阈值，不能自动拒绝假峰或选择通道。
  3. 1550 nm 仅演示值；LiF、折射率和 corrected velocity 未实现。
  4. 全时段 preview 未经过正式质量门，不能当低速正式测量。
  5. GUI、完整 CLI、集成测试、打包和跨机器部署未完成。
- **使用的图**：`基础闭环 ≠ 科研级可信结果` 对照图。
- **图的来源**：当前代码、manifest 解释边界、审计结论。
- **逻辑关系**：把不足转化为明确问题；下一页给出按依赖排序的开发路线。

## 第 14 页：下一阶段优先建立可信判据，再推进修正模型和 GUI

- **本页要回答的问题**：下一阶段应该按什么顺序推进？
- **核心结论**：主线应是非 AI 的可解释谱线增强和质量决策；物理修正必须在波长、窗口材料和模型适用条件确认后接入，GUI 与打包放在稳定工作流之后。
- **正文内容**：
  1. 非 AI 谱线连续性、显式频率范围和物理先验。
  2. 起跳点、平台区与弱信号的可验证判据。
  3. 双通道质量择优：先输出证据，再制定阈值和验收数据集。
  4. 核验波长与 LiF 模型，新增独立 corrected velocity 契约。
  5. 完整 CLI → GUI 工作流 → 打包部署 → 真实用户测试。
  6. AI 只可后期辅助识别，不直接生成最终速度。
- **使用的图**：按依赖关系排列的五阶段路线图。
- **图的来源**：现状缺口推导出的开发计划；属于计划，不是已实现事实。
- **逻辑关系**：从问题自然导出计划；最后一页收束当前结论与近期重点。
